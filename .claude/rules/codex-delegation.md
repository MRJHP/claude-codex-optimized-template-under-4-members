# Codex 위임 규칙

Codex는 `mcp__codex__codex` (신규 세션) / `mcp__codex__codex-reply` (기존 세션 이어가기) MCP 도구로 직접
호출한다. 아래 규칙과 `.claude/hooks/`의 제안은 **강제가 아니라 판단 기준**이다. 실제 호출 여부는 상황에 맞게
Claude가 결정한다.

**사전 승인된 자율 판단**: 사용자는 Codex와의 지속적인 협업을 이미 승인했다. Claude는 아래 기준에
따라 위임이 필요하다고 판단되면 **매번 사용자에게 물어보지 않고** 바로 `mcp__codex__codex`/
`mcp__codex__codex-reply`를 호출한다. 반대로 위임이 불필요하다고 판단되면(아래 "위임하지 않아도
되는 경우") 그 이유를 간단히 밝히고 넘어가면 되며, 이 역시 사용자 확인을 기다릴 필요가 없다. 다만
Codex 호출 자체가 아니라 그 결과를 코드에 반영하는 작업(파일 수정, 커밋 등)은 이 규칙과 별개로
프로젝트의 다른 안전 수칙(예: 파괴적 git 작업 전 확인)을 그대로 따른다.

## 기본 원칙: 모든 작업에 Codex 협업 (진행 전/후)

"의미 있는 변경"(아래 "위임하지 않아도 되는 경우"에 해당하지 않는 모든 코드/설정 변경)에는
더 이상 "고려해야 하는 경우"만 골라 상담하는 게 아니라, **진행 전/후 Codex 협업이 기본값**이다:

1. **진행 전**: 작업을 시작하기 전, 무엇을/왜/어떻게 하려는지 Codex에게 짧게 상담해
   방향·위험·대안을 점검한다.
2. **진행 후**: 작업을 마친 뒤, 실제로 적용한 diff(또는 핵심 변경 요약)를 Codex에게 보여주고
   리뷰를 받는다.
3. 리뷰 결과를 [결과 반영](#결과-반영) 절차대로 판단해서 반영한다.

아래 "Codex에게 위임을 고려해야 하는 경우" 목록은 이 기본값 위에 "특히 더 무겁게, 더 신중하게
상담해야 하는 상황"을 짚어주는 보조 기준으로 남는다.

## Codex에게 위임을 고려해야 하는 경우

1. **구현 전 상담** — 아키텍처/설계에 두 가지 이상의 합리적 선택지가 있거나, 되돌리기 어려운 결정(스키마 변경,
   외부 API 계약 등)을 내리기 전.
2. **구현 후 리뷰** — 파일 여러 개에 걸친 변경, 보안에 민감한 코드(인증, 입력 검증, 시크릿 처리), 동시성/성능이
   중요한 코드를 작성한 직후.
3. **막혔을 때** — 같은 버그를 2회 이상 시도해도 해결하지 못했거나, 원인이 불명확한 실패가 반복될 때 세컨드
   오피니언으로 활용.
4. **사용자가 명시적으로 요청**했을 때.

## 위임하지 않아도 되는 경우

- 오타 수정, 단순 리네이밍, 포맷팅 등 되돌리기 쉬운 사소한 변경.
- 이미 프로젝트에 확립된 패턴을 그대로 반복하는 코드.

## 좋은 위임 프롬프트 작성법

Codex는 이 대화의 맥락을 모르는 상태로 시작한다. 위임 프롬프트에는 다음을 포함한다:
- 무엇을 하려는지와 왜 그런지(배경)
- 관련 파일 경로와 핵심 코드 스니펫 (전체 파일을 읽게 하기보다 필요한 부분만)
- 이미 시도했거나 배제한 접근
- 원하는 응답 형태 (예: "200자 이내로 안전한지 아닌지만 판단해줘")

## 결과 반영

- Codex의 리뷰/제안을 그대로 적용하지 말고, 이 프로젝트의 [coding-principles.md](coding-principles.md)와
  맥락에 맞는지 검토한 뒤 반영한다.
- 중요한 아키텍처 결정에 Codex 의견이 반영되었다면 [DESIGN.md](../docs/DESIGN.md)에 근거를 남긴다.
